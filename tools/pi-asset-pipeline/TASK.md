# Screenshot-to-assets agent pipeline

Your task inputs are ONLY the user's game description (input/description.md) and screenshots in input/screenshots/. Read them yourself with image-capable tools. Do not assume any game, layout, object type, camera, dimensions or cell counts. Operational provider/model/request-budget settings are configured by the runner, not inferred from the images.

Execute the complete pipeline yourself. Do not ask the parent assistant to annotate cells, enumerate objects, choose crops, write game-specific generation prompts or implement your assembly.

1. Inspect every supplied screenshot. Describe observed state separately from rules inferred from the description. Detect whether repeated spatial cells/slots exist. If yes read the game-cell-registration skill and fit/visually verify a grid for each relevant screenshot; if no, use measured scene landmarks and object anchors instead. Never force a grid on a non-grid game.
2. Inventory ALL visible asset instances and distinct poses/states/colors across ALL screenshots. Deduplicate reusable variants without losing viewpoints. Produce asset_map.json with source provenance, coordinates, anchors, visibility versus inferred full geometry, layer order and uncertainties. Choose representative screenshots for reconstruction.
3. Prepare references yourself. For each object/variant supply two images to the image API: contextual crop and crop isolated by a mask. Full screenshots and other workspace images are available for YOUR analysis, not automatically attached to generation. For a grouped sheet provide explicit pairs for represented objects only. Restore complete standalone assets; source occlusion is not a geometric cut. Choose groups yourself. Write prompts grounded in observed proportions, camera, material and colors, not generic stylistic redesign. Generate empty environment and occluders as needed using the same explicit reference contract. Use image_edit.py and the configured model; never expose credentials or silently switch provider/model.
4. Inspect returned art yourself, compare poses at common source scale, record measurements and per-asset verdicts. Reject wrong shapes, cut-off bases, altered states/text or extra outlines before assembly. Preserve all attempts; corrections count toward the same request budget. Extract complete sprites using alpha support, rejecting transparent dust and neighboring contamination.
5. Independently measure generated background geometry and register it to the original. Fit source grid/landmarks before regeneration; identical overlays alone are not registration evidence. Assemble generated assets using measured anchors, isotropic scales and explicit depth layers. Complete sprites are hidden by occluder layers, not destructively trimmed to match visible source fragments. Do not paste original objects/background and label them regenerated.
6. Read stage images and final original-left A/B. Diagnose and correct errors yourself within configured budget. Report real failures and uncertainty. A complete composition does not imply visual fidelity or universal generalization.

## Mandatory independent review loop
Before image generation call the GEOMETRY critic. Before final assembly call the ASSETS critic, covering every variant in asset_map, including environment/UI. After reconstruction call SCENE critic. You are the builder, never write critic verdicts yourself. Prepare a manifest JSON: {"items":[{"id":"your item id","files":["source image/crop","candidate image/overlay","measurement metadata"]}]}. Include all originals needed, all candidates and evidence. Call `python3 critic.py --stage geometry --manifest output/geometry_review.json` (analogous assets/scene). This launches a NEW read-only agent, not your own self-review. Exit 2 means revise OR uncertain: read the report, repair yourself, then re-review changed artifacts. Maximum three reviews per stage, same image request budget across all repairs. Reserve some image budget for critic-directed corrections rather than spend all before review. Prioritize geometry-refit/local extraction/registration/placement fixes before expensive regeneration. Never silently bypass a gate; if exhausted or uncertain, preserve a provisional output and report which gate failed.

GEOMETRY manifest must include source-only observations, at least two competing boundary/phase hypotheses when ambiguous, overlays for each, explicit floor versus raised-wall evidence and held-out central/distant landmarks not used in fitting. Select using visible source evidence, not guessed object bottoms, fit residual alone, or remembered coordinates. Account for irregular/perspective geometry; absent grid is valid. Critic disagreement requires renewed source inspection, not another confident assertion.

ASSETS manifests cover every identified variant/state/pose. Supply contextual+masked source images and generated extracted candidates; compare at common isotropic scale, record visibility masks and inferred hidden completion separately. Every non-pass item must be addressed or marked provisional. SCENE manifest includes original, complete reconstruction, registration/occlusion evidence and asset map; critic must reread the whole scene. Store immutable reports/traces in output/critics; changed reviewed files invalidate hash-bound acceptance. Include latest gate status and exact remaining budgets in report.md.

Required outputs under output/: game_description.md, asset_map.json, source geometry/grid-or-landmarks JSON and overlays, contextual/masked references, generated images, extracted sprites, registration evidence, reconstruction(s), final_ab.png, report.md, and executable local replay scripts. For gridless games report grid detection as not applicable. Report exact submitted/success/failed/unconfirmed image counts from the wrapper's append-only ledger. Never resubmit generation during local replay.

Scope: only the isolated run directory. No historical sample outputs, manually supplied geometry or hidden game-specific scripts as authority. No global/DSH edits. Local processes below 2 GiB; no heavy local neural inference. No ad-hoc subagents; the provided independent critic.py is mandatory. The concrete run may produce game-specific measured data/code, but reusable prompts/skills MUST remain game-agnostic.
